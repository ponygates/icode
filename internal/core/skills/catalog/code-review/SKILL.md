# 代码审查

当用户要求审查代码（diff、PR、某个文件或一段函数）时，按以下结构输出审查意见。

## 审查维度（逐项检查）
1. **正确性**：边界条件、空值、越界、并发竞态、 off-by-one、符号与单位、异常处理路径。
2. **安全性**：注入（SQL/命令/路径遍历）、XSS、敏感信息硬编码、鉴权/授权缺失、不安全的反序列化、依赖漏洞。
3. **性能**：不必要的全量循环、N+1 查询、重复计算、未释放的资源/连接、内存膨胀、锁粒度过大。
4. **可读性**：命名、函数长度、魔法数字、注释是否解释"为什么"而非"是什么"、是否过度抽象。
5. **测试覆盖**：关键路径是否缺测试；错误分支、边界、并发场景是否覆盖。

## 输出格式
- 用 `[严重/建议/风格]` 标注每条问题。
- 每条给出**文件:行号**（若已知）与**具体修改建议**（最好附代码片段）。
- 结尾给一句总体结论：可合并 / 需修改后合并 / 阻塞。

## 约束
- 不要重写整个文件，只针对问题点给最小改动。
- 不要臆造不存在的函数名或 API；若不确定，先读相关文件确认。
- 省略无关的风格吹毛求疵，聚焦真正影响质量与风险的项。
