## 一、P1（1 项，已修复）

### #1 桌面 SSE 流被 115s/120s 硬上限斩断 — 已修复

**发现**：`handlers_chat.go:126` 的 `context.WithTimeout(r.Context(), 115*time.Second)` 配合 `server.go:259` 的 `WriteTimeout: 120 * time.Second`，把任何超过 ~2 分钟的桌面端 agentic 回合中途杀死。

- **影响面**：桌面端、simpleui 内嵌 UI、VS Code 扩展——凡经 HTTP `/api/chat` SSE 路径的入口。CLI/TUI 直连 `engine.Send`（不经 http.Server）不受影响，故此前所有 CLI 测试与日志未能暴露。
- **为何致命**：单回合默认跑 25 轮工具（`max_tool_rounds`），每轮含模型流式（30–90s）+ 构建/测试（10–60s），合法回合 routinely 超 2 分钟。超时触发后引擎走 `ctx.Done()` 分支，持久化部分输出并返回「⏹ 已中断生成」——用户看到的是「桌面端每次跑到 2 分钟就停」。
- **根因**：115s 是当时为「赶在 120s WriteTimeout 前优雅取消」而设的妥协，等于承认长回合必断；Go 的 `http.Server.WriteTimeout` 是响应总时长绝对上限（非每次写入重置），对 SSE 天然不兼容。

**修复**：
- `server.go:259`：`WriteTimeout: 0`（禁用绝对写超时），注释说明 SSE 需无界写。Liveness 改由 `r.Context()`（客户端断连即取消）+ 引擎 `maxToolRounds` 上界 + provider HTTP 客户端兜底共同保证。
- `handlers_chat.go:126`：`context.WithCancel(r.Context())` 取消 115s 硬上限，回合寿命=客户端连接寿命（断连即中断+保留部分输出，与 Claude Code parity 一致）。
- **验证**：server 包 25 测试全绿；全量 787 测试全绿。
