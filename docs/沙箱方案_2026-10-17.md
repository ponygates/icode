# iCode 操作系统级沙箱方案（P0-1）

> 状态：**批次 1 已实现并验证**（Windows AppContainer + bash 前台接入，v0.3.0）。批次 2–5 见第六节。
> 本机（Windows 10 Pro / x64）已完成端到端实测；Linux 与 macOS 分支尚未实现，文中逐项标注。
> 前置审查：`docs/项目审查_2026-10-17.md` 的 P0-1「缺少操作系统级沙箱」。
>
> 已确认的两项设计选择：`mode` 默认 `auto`；首次启用时在工作目录写入 AppContainer ACE，并提供撤销入口（`sandbox.RevokeWorkspace`）。

---

## 一、要解决的问题

### 现状：防护是字符串级的，沙箱是文件工具专用的

| 层 | 位置 | 覆盖 | 绕过方式 |
|---|---|---|---|
| 权限门 | `permission/gate_rules.go:222` `outsideAllowedPaths` | 仅 `action.Path != ""` 的工具 | **bash 的自由命令通常没有 path 参数**，直接穿透 |
| 规则引擎 | `permission/bashsec.go` 23 条正则 | 已知危险形态 | 变量拼接、`$(base64 -d)`、`r''m -rf`、别名 |
| 执行 | `tool/tools_bash.go:159`、`tool/bgtask.go:230`、`server/handlers_shell.go:53` | 无 | `cmd.Dir` 之外无约束，环境变量完整继承 |

结论：只要模型能写出一条不在黑名单里的命令，它就拥有了**当前用户的完整权限**——读私钥、改启动项、外发数据。这不是"规则不够多"的问题，是防护位置错了：正则跑在进程创建之前，攻击面在进程创建之后。

### 目标

1. 让 bash 的**每一次执行**都落在 OS 强制的边界内，规则绕过不影响边界。
2. 边界内正常工作：`go build`、`npm test`、`git status` 不因此失效。
3. 不可用时**显式降级**，绝不假装安全。
4. 用户可关（`off`），但关闭时要有醒目提示。

### 非目标

- 不替代权限门。沙箱是最后一道闸，不是第一道。
- 不做网络代理级拦截（本期只做"允许 / 拒绝"二值，域名白名单留后续）。
- 不隔离模型/API 流量（用户需要它访问外网）。

## 二、三平台机制对照

| 平台 | 机制 | 隔离维度 | 依赖 | 本机可验证 |
|---|---|---|---|---|
| Windows | **AppContainer** + `STARTUPINFOEX` | 文件读/写、注册表、网络、命名对象 | 无（Win8+ 系统内置） | ✅ 已完成 |
| Linux | **bubblewrap**（首选）→ **Landlock**（回退） | 文件、网络、PID、IPC | bwrap 需安装；Landlock 需内核 5.13+ | ❌ 需 Linux 机器 |
| macOS | **`sandbox-exec`** + SBPL profile | 文件、网络、进程 | 系统内置（虽标 deprecated，仍是唯一现实选项） | ❌ 需 macOS 机器 |

选型理由：

- **Windows 不用 Low Integrity Level**：IL 是 `no-write-up` 语义，只拦写不拦读，`type ~/.ssh/id_rsa` 照样成功，达不到验收标准。
- **Windows 不用 Job Object 单独承担**：Job Object 管进程/内存/CPU，不管文件系统，只能作为辅助。
- **Linux 首选 bwrap 而非直接 Landlock**：bwrap 的语义等价于容器，可一次性表达挂载与网络策略，且是 Codex CLI 的既有选择；Landlock 作为无依赖回退。
- **macOS 不用 cgo 绑 Seatbelt**：SBPL 文本 profile 已足够，cgo 会让交叉编译与纯 Go 构建复杂化。

## 三、Windows 分支：已实测的结论

### 3.1 实测结果

探针程序用 `syscall` 手写 `CreateProcessW` + `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`，在 `icode-sandbox` 这个 AppContainer 内执行命令：

| # | 命令 | 期望 | 实测 | 结论 |
|---|---|---|---|---|
| A | `type C:\Users\Administrator\.ssh\known_hosts` | 拒绝 | `exit=1`「拒绝访问」 | ✅ 读私钥被拦 |
| B | `dir C:\Users\Administrator\Desktop` | 拒绝 | `exit=1`「拒绝访问」 | ✅ 用户目录不可枚举 |
| C | `type C:\Windows\win.ini` | 允许 | `exit=0` 正常输出 | ✅ 系统公共文件可读 |
| D | `echo x > C:\Windows\Temp\probe_evil.txt` | 拒绝 | `exit=1`「拒绝访问」 | ✅ 系统目录不可写 |
| E | `echo hello > out.txt`（cwd 未授权） | 拒绝 | `exit=1`「拒绝访问」 | ⚠️ **工作区必须显式授权** |

A/B/D 是这次最关键的三个数据点：**读和写都真的被内核拦住了**，不是靠规则判断。C 说明不是"全禁"，公共只读文件仍可用。

### 3.2 E 的后果：工作区授权是必需项，不是可选项

AppContainer 令牌里没有当前用户 SID，也没有 `Users` 组，所以项目目录默认对它不可见。**必须先给工作区目录加一条 ACE**，否则连 `cmd` 都无法以该目录为 cwd 启动（实测报「当前目录无效」）。

这是本方案**唯一有持久副作用的动作**，必须让用户知情：

- ACE 形如 `S-1-15-2-<hash>:(OI)(CI)(F)`，写在项目目录的 DACL 上；
- 可撤销（删掉该 ACE 即恢复原状）；
- 建议在**首次启用沙箱时**执行一次，并在设置页提供「撤销沙箱授权」按钮；
- 不做静默授权。

### 3.3 实现坑（已踩，供后续参考）

1. `SECURITY_CAPABILITIES.Reserved` 是 **`DWORD`**，不是 `DWORD64`。写成 `uint64` 会让结构体从 24 字节变 32 字节，`UpdateProcThreadAttribute` 直接返回 `ERROR_INVALID_PARAMETER`（0x57），错误信息是「参数错误」，很难定位。
2. `ConvertSidToStringSidW` 在 **advapi32**，不在 kernel32。
3. `CreateAppContainerProfile` 在 profile 已存在时返回 `0x800700B7`（`HRESULT_FROM_WIN32(ERROR_ALREADY_EXISTS)`），此时改用 `DeriveAppContainerSidFromAppContainerName`。
4. Go 标准库 `os/exec` **不支持** `STARTUPINFOEX`（`syscall.SysProcAttr` 没有对应字段），必须自建管道 + `CreateProcessW`。
5. **传 UTF-16 环境块必须同时置 `CREATE_UNICODE_ENVIRONMENT`（0x400）**。漏掉时系统按 ANSI 解析，每个条目解码成空变量名，`CreateProcess` 返回 `ERROR_ENVVAR_NOT_FOUND`（203）。
6. **`*uint16` 转 `uintptr` 后 GC 不再追踪**。环境块必须先存入具名变量并在调用后 `runtime.KeepAlive`，否则可能在 `CreateProcess` 期间被回收，表现为子进程无声卡死。

### 3.3b NUL 设备：唯一的硬缺口，已解决

`\Device\Null` 的默认 DACL 是：

```
D:(A;;0x1201bf;;;WD)(A;;FA;;;SY)(A;;FA;;;BA)(A;;0x1200a9;;;RC)
```

即 `Everyone / SYSTEM / Administrators / Restricted Code`，**没有 AppContainer 组**。AppContainer 令牌里的 `Everyone` 是 deny-only，因此容器内 `echo hi > NUL` 与 `type NUL` 都会被拒。

这不只是小问题：Go 工具链计算 build ID 时会 `open NUL`，`go build` 于是直接失败——`go: error obtaining buildID for go tool compile: open NUL: Access is denied.`

解决办法是给该设备补一条容器 SID 的 ACE。实测在管理员账户下 `SetNamedSecurityInfo("NUL", ...)` 可以成功，后端在初始化时幂等执行（已存在则跳过），并在 notice 中告知用户。设备本身是个黑洞，不存任何数据，因此不扩大实质暴露面。

DACL 不可写时（普通用户账户），后端不阻断启动，只记录一条 notice 说明「沙箱内可能无法构建」。

### 3.4 工作量

Windows 分支实测约 **560 行**（进程创建 260 + 策略/ACL 180 + 环境与探测 120），其中进程创建部分先在独立的探针程序里跑通再收敛，避免了把调试成本带进主代码。

## 四、统一接口

沙箱不能只挂在 `BashTool` 上——共有三个执行点，漏一个就等于没做：

1. `tool/tools_bash.go` — 模型调用的前台命令
2. `tool/bgtask.go` — 模型调用的后台任务
3. `server/handlers_shell.go` — 用户 `!` 快捷方式（信任级别不同，默认**不**沙箱）

```go
package sandbox

type Mode string

const (
    ModeAuto Mode = "auto" // 平台支持就启用，否则告警后降级
    ModeOn   Mode = "on"   // 必须启用；不可用则拒绝执行
    ModeOff  Mode = "off"  // 显式关闭，配合醒目告警
)

type Spec struct {
    Dir      string        // 工作目录（自动纳入可写集）
    Writable []string      // 额外可写路径（默认追加系统临时目录）
    Network  NetworkPolicy // NetworkDeny（默认）| NetworkAllow
    OnOutput func([]byte)  // 流式输出回调，替代当前的 progress 机制
}

type Handle interface {
    Wait() (Result, error)
    Kill() error
}

type Result struct {
    Output   string
    ExitCode int
    Truncated bool
}

// Runner 是一个已就绪的沙箱后端。启动时探测一次，全程复用。
type Runner interface {
    Name() string          // "appcontainer" | "bwrap" | "seatbelt"
    Available() bool
    // Prepare 确保 Spec.Dir 可访问（含必要的授权），返回可执行的 Runner。
    Prepare(Spec) error
    Start(ctx context.Context, command string, spec Spec) (Handle, error)
    Close() error
}

// Detect 返回当前平台的最佳后端；都不可用时返回 noop（Available=false）。
func Detect(mode Mode) (Runner, error)
```

关键约束：

- `Runner.Start` 自己管进程，**不接收 `*exec.Cmd`**。Windows 无法用 `exec.Cmd` 表达 `STARTUPINFOEX`，硬套接口会导致 Windows 分支另开一条路。
- `Spec.OnOutput` 取代 `ProgressFromContext` 在 bash 工具里的用法，顺带解决 bgtask 与前台两条路径输出逻辑不一致的问题。
- `handlers_shell.go` 先不接入：它是用户自己敲的命令，与"模型自主执行"的威胁模型不同。列为二期，且默认 `Mode=yolo` 时也不沙箱。

## 五、配置与降级语义

```yaml
sandbox:
  mode: auto            # auto | on | off
  writable_paths: []    # 额外可写目录，工作区与临时目录自动加入
  network: deny         # deny | allow
```

| mode | 后端可用 | 后端不可用 |
|---|---|---|
| `auto`（默认） | 静默启用 | **一次性醒目告警**（TUI/桌面各一处），继续无沙箱执行 |
| `on` | 静默启用 | **拒绝执行 bash**，返回可读错误：「当前平台不支持内核沙箱，请改用 security.sandbox=off 显式承担风险」 |
| `off` | — | 每次进入 `yolo` 模式时提示：「沙箱已关闭，模型命令以你的完整权限运行」 |

降级必须可观测：`/status` 与设置页「安全沙箱」区块显示**当前实际生效的后端**（`appcontainer` / `bwrap` / `未启用（不支持）`），而不是只显示配置值。这是"声明了 ≠ 接通了"的防线。

## 七、验收标准

沙箱启用（`mode=on`）时必须全部满足：

| # | 用例 | 判定 |
|---|---|---|
| 1 | `bash -c 'echo x > ~/outside.txt'` | 拒绝，错误可读 |
| 2 | `cat ~/.ssh/id_rsa`（或 `known_hosts`） | 拒绝 |
| 3 | `ls ~/Desktop` / `dir %USERPROFILE%\Desktop` | 拒绝 |
| 4 | `go build ./...`、`git status`、`npm test` | 正常完成 |
| 5 | 工作区内 写文件 / 删文件 | 正常完成 |
| 6 | `curl https://example.com`（`network=deny`） | 拒绝且提示网络策略 |
| 7 | 子进程（`go build` 派生的编译器）继承边界 | 继承，不逃逸 |
| 8 | `mode=off` | 行为与今天完全一致 |
| 9 | 后端不可用 + `mode=on` | 拒绝执行，不静默放行 |
| 10 | 授权撤销后 | 工作区立即不可访问（确认 ACE 真的被删除） |

用例 7 需要专门测：Windows 的 AppContainer 令牌**默认对子进程继承**，但要确认 `go build` 调用 `compile.exe` 时不因缺少能力而失败。

## 八、风险与待确认

| 风险 | 说明 | 应对 |
|---|---|---|
| 项目目录 ACL 被修改 | 唯一持久副作用，可能引起版本库/备份工具告警 | 首次启用需用户确认；提供撤销；ACE 只加不删其它项 |
| 工具链兼容性 | 部分构建工具（如依赖用户级缓存的 `go`、`npm`）可能因无法写 `~/.cache` 而失败 | `writable_paths` 可扩展；验收用例 4 实测把关 |
| 性能 | 每次命令多一次 `CreateProcess` 与 ACL 检查，预计 < 50ms | 立即可接受，无需优化 |
| 环境变量 | AppContainer 下 `%USERPROFILE%` 指向容器目录 | 需在 `Spec` 里显式注入 `HOME`/`TMP`/`TEMP` 映射 |
| 本机无法验证 Linux/macOS | 只能靠代码审查 + 平台自测脚本 | 明确不声称已验证；留待有机器时补测 |

**需要你确认的两点**：

1. 是否接受「首次启用沙箱时，在项目目录 ACL 上添加一条 AppContainer SID 的 ACE」这个副作用（可撤销）。
2. 是否同意 `mode` 默认值取 `auto`（支持就启用，不支持则告警后降级），而不是 `on`（不支持就拒绝执行）。`auto` 的兼容性更好，`on` 的安全性更强。
